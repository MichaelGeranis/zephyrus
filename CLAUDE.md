# Zephyrus — Claude Code Project Brief

> Like the west wind that nourishes the Elysian Fields, Zephyrus breathes life into ideas —
> turning prompts into PRDs, architecture, code, tests, and deployed software through a
> pipeline of specialized AI agents with human validation at every gate.

---

## What You Are Building

Zephyrus is an AI-powered software delivery platform that orchestrates the full journey
from idea to production. It is designed for a **3-person amplified team** that produces
the output of 10, by placing AI agents at every execution step and humans at every
validation gate.

**The core loop:**
```
Idea (prompt) → PRD → Architecture → Tasks → Code → QA → Deploy
```

Each step is executed by a specialized AI agent. No step advances without explicit human
approval (at the moment). GitHub is the delivery layer — all artifacts live there.

## The 3-Person Team Model

| Role | Domain | Responsibility |
|------|--------|---------------|
| Product & Engineering Manager | Responsible and Accountable for Delivery Excellence, Project Management, People Management, Product Ideation => Vision & Delivery | Writes idea prompts, approves PRD, prioritizes features |
| Tech Lead | Architecture & Code | Responsible and Accountable for Technical Excellense => Reviews architecture decisions, validates PRs |
| QA | Quality & Correctness | Responsible and Accountable for the Quality Excellence => Defines acceptance criteria, approves test results |

These are **amplified roles** — each person must retain enough technical knowledge to
troubleshoot and override AI output when needed.

## Architecture
Clean Architecture as described by Uncle Bob at the Clean Architecture book.

Separation of Concerns: Clearly separating business rules (inner layers) from infrastructure details (outer layers).
The Dependency Rule: Inner layers know nothing about outer layers; dependencies point toward the center.
Independent of Frameworks/UI/DB: Core business logic is not bound to external tools, making it easy to change or swap them.
Testable: Business rules can be tested without the user interface, database, or web server.
SOLID Principles: Utilizes these principles to ensure code is maintainable, flexible, and robust.

### Frontend Rules
- Zephyrus.Web is a thin presentation layer — no business logic whatsoever
- All validation, state transitions, and orchestration happen server-side in the .NET backend
- The frontend calls the API and renders the response — nothing more

## The Pipeline — Stage by Stage

### Stage 1: Idea Input
- Human (PM+EM) writes a free-text prompt describing the feature
- No agent involved — raw human input
- Stored as `Feature.prompt` in the database

### Stage 2: PRD Generation
- **Agent:** PRD Agent
- **Input:** `Feature.prompt` + `Project Constitution`
- **Output:** Structured markdown PRD containing:
  - Problem statement
  - Target users
  - Goals & non-goals
  - User stories in `Given / When / Then` format
  - Acceptance criteria
  - Open questions
- **Artifact:** `/docs/prd-{feature-slug}.md` committed to repo
- **Gate:** PM+EM reviews, edits inline if needed, marks approved

### Stage 3: Architecture
- **Agent:** Architect Agent
- **Input:** Approved PRD + `Project Constitution`
- **Output:** Architecture Decision Record (ADR) containing:
  - New components or services needed
  - DB schema changes (tables, columns, relations)
  - API contracts (endpoints, request/response shapes)
  - External dependencies
  - Estimated complexity per area
- **Artifact:** `/docs/adr-{feature-slug}.md` committed to repo
- **Gate:** Tech Lead reviews, approves or requests changes

### Stage 4: Task Breakdown
- **Agent:** Task Agent
- **Input:** Approved PRD + approved ADR + `Project Constitution`
- **Output:** Ordered list of atomic, independently implementable tasks
- Each task contains:
  - Title
  - Context (why this task exists)
  - Acceptance criteria
  - Dependencies (other task IDs)
  - Agent type: `BE | FE | DB | DevOps`
- **Artifact:** GitHub Issues, labeled and milestoned
- **Gate:** PM+EM approves scope, Tech Lead approves ordering and granularity

### Stage 5: Code Generation
- **Agent:** Code Agent (one invocation per GitHub Issue)
- **Input:** Single GitHub Issue + ADR + `Project Constitution` + relevant existing code
- **Output:** Implementation satisfying the issue
- **Artifact:** Feature branch + PR linked to the Issue
- **Note:** Parallelizable where task dependencies allow
- **Gate:** Tech Lead reviews PR diff

### Stage 6: QA & Testing
- **Agent:** QA Agent
- **Input:** PR diff + original Issue + acceptance criteria + `Project Constitution`
- **Output:**
  - Unit tests
  - Integration tests
  - Test run summary: pass / fail / coverage %
  - If failed: annotated diff of what broke and why
- **Artifact:** Test files committed to PR branch + CI run report as PR comment
- **Gate:** QA reviews test coverage, approves or requests fixes

### Stage 7: DevOps & Deployment
- **Agent:** DevOps Agent (runs once at project setup, then on config change)
- **Input:** `Project Constitution` + deployment target
- **Output:** GitHub Actions CI/CD workflow
- **Artifact:** `.github/workflows/deploy.yml`
- **Gate:** Tech Lead reviews and merges
- **Deployment:** Automatic on merge to main

## The Project Constitution

The Project Constitution is a YAML config file the Tech Lead fills out once per project.
**Every agent reads it before acting.** It is the context spine — the baton passed between
all agents.

```yaml
project:
  name: my-app
  description: "Brief description of what this project does"

stack:
  frontend: "Next.js + TypeScript"
  backend: "ASP.NET Core + C#"
  database: "PostgreSQL"
  orm: "Entity Framework Core"

conventions:
  linting: "ESLint + Prettier (frontend), dotnet format (backend)"
  testing: "Jest (frontend), xUnit (backend)"
  branch_strategy: "feature branches → main"
  commit_style: "conventional commits"
  pr_template: true

deployment:
  target: "Railway"
  trigger: "merge to main"
  environment_variables:
    - DATABASE_URL
    - CLAUDE_API_KEY
    - GITHUB_TOKEN

architecture:
  patterns:
    - "Repository pattern for data access"
    - "CQRS for API handlers"
    - "Stateless agents — all state in DB and GitHub"
  api_style: "REST + JSON"
  auth: "JWT"
```

### Feature State Machine

```
ideation
  → prd_pending         (PEM submits prompt)
  → prd_approved        (PEM approves PRD)
  → arch_pending        (PRD approval triggers Architect Agent)
  → arch_approved       (TL approves ADR)
  → tasks_pending       (ADR approval triggers Task Agent)
  → tasks_approved      (PEM + TL approve tasks)
  → coding              (Task approval triggers Code Agents)
  → qa_pending          (All PRs open, triggers QA Agent)
  → qa_approved         (QA approves tests)
  → deployed            (TL merges, CI/CD deploys)
```

## The Orchestrator

The Orchestrator is a **deterministic state machine** — not an AI. It:

1. Listens for approval events from the UI
2. Listens for GitHub webhook events (PR merged, CI passed/failed)
3. Builds the correct context bundle for the next agent
4. Invokes the next agent asynchronously via the job queue
5. Persists state transitions to `PipelineEvent`

```csharp
// Pseudocode — the core orchestration logic
public async Task OnArtifactApproved(Guid featureId, ArtifactType type)
{
    var feature = await _repo.GetFeatureAsync(featureId);
    var nextStatus = _stateMachine.GetNextStatus(feature.Status);

    if (await AllDependenciesMet(feature, nextStatus))
    {
        await _jobQueue.EnqueueAsync(new AgentJob(featureId, nextStatus));
        await _repo.UpdateStatusAsync(featureId, nextStatus);
    }
}
```

**Key rule:** Agents are stateless. The Orchestrator is stateful. Never put state inside an agent.

## Agent Design Pattern

Every agent follows this contract:

```csharp
public interface IAgent<TInput, TOutput>
{
    Task<TOutput> RunAsync(TInput input, CancellationToken ct);
}
```

Every agent call to Claude API:
1. Loads the appropriate system prompt for that agent type
2. Assembles context: `Project Constitution` + relevant artifacts + (optional) existing code
3. Calls Claude API via `HttpClient`
4. Parses structured output (JSON or Markdown depending on agent)
5. Commits artifact to GitHub via Octokit.net
6. Returns result to Orchestrator

**Retry policy:** Agents can be retried freely — they are stateless. On QA failure, the
Code Agent is retried once with the failure report injected as additional context.
After one retry, escalate to human.

## GitHub Integration Rules

- **Never duplicate code artifacts in the DB** — GitHub is source of truth for all code
- Branch naming: `feature/{feature-slug}/{task-id}`
- PR title format: `[Zephyrus] {task-title} (#{issue-number})`
- All PRs are linked to their originating GitHub Issue
- Webhook events drive pipeline state advancement where possible
- Fallback: polling every 60 seconds for missed webhooks

## Build Order

Implement in this exact order. Each step unblocks the next.

1. **DB schema + EF Core migrations** — the skeleton everything hangs on
2. **GitHub integration layer** — `Zephyrus.GitHub`: create branch, commit file, open PR, create issue
3. **PRD Agent** — first agent end-to-end: Claude API call → markdown output → committed to repo
4. **Approval gate API** — `POST /features/{id}/artifacts/{artifactId}/approve` — reusable pattern
5. **Approval gate UI** — Next.js view: show artifact content, edit inline, approve button
6. **Orchestrator state machine** — wire PRD approval → trigger Architect Agent
7. **Architect Agent** — same pattern as PRD Agent, different prompt + output structure
8. **Task Agent** — output is GitHub Issues, not a markdown file
9. **Code Agent** — most complex: reads existing code, outputs PR
10. **QA Agent** — reads PR diff, outputs test files + CI report
11. **DevOps Agent** — generates GitHub Actions workflow
12. **Pipeline dashboard UI** — visualize feature status across all stages

## What NOT to Build in MVP

- RAG / vector search (add post-MVP when repo exceeds ~100k tokens)
- Multi-repo support
- Multi-cloud / multi-environment deployment
- Infinite agent retry loops (one retry then human escalation)
- Multi-project portfolio view
- Mobile stack support (React Native, Flutter)
